# 오프라인 하네스 교육 예제

이 코드는 **AI가 만든 교육용 설계 보완 예제**다. 실제 강의 실습을 재현하거나 사용자의 구현 성과를 증명하는 코드는 아니다. Python 3.10 이상과 표준 라이브러리만 사용한다. 실제 모델, MCP 서버, 네트워크, 파일 저장은 사용하지 않는다.

가상의 요청은 “공개 메모를 읽고, 사용자가 검토한 초안을 저장하자”다. `ScriptedModel`은 미리 정한 제안을 반환한다. 하네스는 그 제안을 받았다고 바로 실행하지 않고 형식, 허용 자원, 승인, 중복 키, 호출 한도를 차례로 검사한다. `save_draft`의 저장 대상은 메모리 목록이므로 프로그램이 종료되면 사라진다.

가이드 루트에서 실행한다.

```powershell
python examples/harness/harness.py
python -m unittest discover -s examples/harness -v
```

첫 명령은 읽기 성공, 초안 저장 성공, 정상 완료의 JSON 이벤트 세 줄을 출력한다. 본문, 사용자 식별자, 승인 토큰, 예외 메시지는 이벤트에 넣지 않는다. 결과 객체에는 모델이 다음 결정을 할 때 필요한 읽기 값이 포함될 수 있으므로, `results` 자체를 로그로 출력하지 않는다.

## 무엇을 확인하는가

`harness.py`의 `execute()`가 도구 실행 경계다. 모델은 허용된 도구 이름과 정확한 인자 필드를 제안해야 한다. 알 수 없는 이름, 추가 필드, 잘못된 타입, 너무 긴 값은 `invalid_action`이다. 읽기 자원은 `public`과 `missing`이라는 고정 키만 허용한다. 이는 파일 경로 허용 목록 예제가 아니므로 임의 경로나 파일 시스템을 읽지 않는다.

| 상태 | 이 예제에서의 의미 |
|---|---|
| `ok` | 읽기 또는 초안 저장이 성공함 |
| `missing_data` | 허용된 읽기 자원이 존재하지 않음 |
| `denied` | 자원이 허용 목록 밖에 있음 |
| `approval_required` | 승인 없음, 인자/사용자/버전 불일치 또는 승인 만료 |
| `conflict` | 같은 범위의 중복 키에 다른 내용이 들어옴 |
| `invalid_action` | 제안 형식이나 도구 이름이 계약에 맞지 않음 |
| `error` | 제공자 오류, 잘못된 제공자 결과 또는 모델 오류 |
| `limit_reached` | 단계, 실제 도구 호출 수 또는 모의 비용 한도에 도달함 |
| `completed` / `stopped` | 모델의 명시적인 완료 / 중단 제안 |

누락과 거부는 다르다. 없는 자료는 다음 판단에 관찰값으로 전달할 수 있지만, 거부를 “자료가 없었다”로 바꿔 말하면 권한 문제를 숨기게 된다. 여기서는 `ok`와 `missing_data`만 다음 모델 단계로 이어지고 나머지는 즉시 실행 루프를 끝낸다.

`approve()`는 신뢰된 사용자 승인 화면의 대역이다. 데모의 승인 호출은 **이미 사용자가 구체적인 초안을 검토했다는 가정**을 코드로 나타낸다. 실제 사용자 동의를 수집하지 않는다. 모델에 `approve()`를 도구로 노출하지 않는다. 승인에는 사용자, 작업 버전, 실행 ID(`run_id`), 도구 이름, 정렬된 JSON 인자, 만료 시각이 묶인다. `now >= expires_at`이면 만료된다. 신뢰된 승인 레지스트리에서 조회한 값과 비교하므로 본문이 바뀌면 다시 승인이 필요하다. 데모의 순차 토큰은 인증용 비밀이 아니며, 이 레지스트리와 메서드는 신뢰 경계 안에 있어야 한다.

중복 키 범위는 `(사용자, 버전, 실행 ID, 도구, idempotency_key)`다. 승인 검사는 중복 조회보다 먼저 수행하므로 승인 만료 뒤의 재전송도 거절된다. 유효한 승인 아래 같은 범위와 같은 정규화 내용이 다시 오면 기존 결과를 반환하고 목록에 두 번 추가하지 않는다. 같은 키에 다른 내용이면 `conflict`이며, 키가 같아도 사용자가 다르면 별도 작업이다.

읽기에서 `TransientReadError`만 최대 `read_attempts`회 시도하며 설정 자체도 1~3회로 제한한다. 각 실제 시도 전에 호출 수와 비용을 차감한다. 일반 오류, 거부, 쓰기는 재시도하지 않는다. 재시도 한도를 남겨 두어도 전역 예산이 먼저 끝나면 중단한다. 이 예제는 대기 없이 결정적으로 실행된다.

`max_steps`는 모델 제안 횟수이고 완료 제안도 한 단계다. `max_tool_calls`는 재시도를 포함한 실제 제공자 호출 및 최초 초안 저장 횟수다. `budget`은 호출당 1을 사용하는 **모의 정수 비용**으로, 토큰·실제 요금·실행 시간 한도가 아니다.

객체 하나는 논리 실행 하나다. `run()`이 완료·중단·오류·한도로 끝나면 객체가 닫히고, 이후 `run()`과 `execute()`는 `denied/run_closed`를 반환한다. 새 실행은 새 객체, 신뢰된 호출자가 지정하는 새 `run_id`, 새 승인이 필요하다. 직접 `execute()`를 호출하는 것은 루프 전에 경계를 단위 검증하기 위한 인터페이스이며, 전체 실행의 단계 제한은 `run()`이 담당한다.

## 검증 기록과 생략한 부분

테스트를 먼저 작성한 뒤 실행했을 때 구현 파일이 없어 `ModuleNotFoundError`로 실패했다. 구현 후 위 unittest 명령으로 12개 테스트가 모두 통과했다. 실행 ID 변경과 종료 후 승인 재사용을 확인하는 회귀 테스트 두 개도 수정 전에 실패하고 수정 후 통과했다. 테스트는 정상 완료와 중단, 거부와 미승인, 인자 변경과 사용자/버전 변경과 만료, 동일 키 재사용과 내용 충돌과 사용자 범위, 단계/호출/예산 한도, 잘못된 제안, 누락/오류 구별, 읽기 재시도 한도 및 로그의 본문/토큰 제외를 확인한다.

이 코드는 단일 프로세스·단일 스레드 안의 학습용 상태를 다룬다. 영속 저장, 트랜잭션, 프로세스 간 중복 제거, 장애 후 복구, 정확히 한 번 실행을 보장하지 않는다. 실제 서비스에서는 작업 결과와 중복 처리 기록의 원자적 저장, 실제 인증·권한과 승인 UI, 시간/토큰 비용 제한, 호출 취소와 타임아웃, 재시도 지연, 외부 응답 검증과 신뢰 구분을 별도로 설계해야 한다. 모델이나 제공자가 무한 대기하면 이 예제의 횟수 한도만으로 중단시킬 수 없다. MCP 전송 및 인증도 구현하지 않았으며, 이 구조를 MCP에 적용할 때에도 서버 연결 성공을 업무 권한 승인으로 해석해서는 안 된다.
