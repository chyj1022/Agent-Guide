## 왜 필요하고 무엇인가

외부 에이전트 내부를 알지 못해도 능력, 접속과 인증 정보를 읽고 위임 여부를 결정할 수 있어야 한다. Agent Card와 작업 상태는 발견과 실행 추적의 서로 다른 계약이다.

## 입력에서 출력까지

상대의 이름, 설명, 버전, 전송 방식, 기능, 인증과 입출력 모드를 확인한다. 작업 접수 뒤 ID를 저장하고 진행, 입력 필요, 인증 필요, 완료, 실패, 취소와 거절을 구별해 처리한다. 완료 결과도 검증한다.

## 원자료의 구체적인 설명

배송 카드 예시는 견적과 예약 스킬, 스트리밍과 푸시 알림, OAuth 범위를 공개한다. 서울에서 부산으로 3kg 박스를 보내는 견적과 특정 견적 ID 예약이 다른 능력이다. 상태표는 failed와 rejected를 다른 재시도 대상으로 설명한다.

## 적합한 조건과 피할 조건

능력 기반 발견과 비동기 업무 위임에 적합하다. 카드를 읽었다는 이유로 상대의 신원과 품질까지 검증됐다고 보거나 모든 종료 상태를 재시도하는 방식은 부적절하다.

## 한계와 확인할 점

카드는 자기 설명이다. 서명과 신뢰된 발급자, 실제 엔드포인트 정책을 따로 확인해야 한다. 상태의 정확한 문자열과 전이는 구현한 A2A 버전의 스키마를 따른다.

## 설계 적용, AI 보완

상태별 사용자 안내와 재시도 가능성을 명시한다. input_required는 질문으로, 인증 필요는 안전한 인증 흐름으로 보내고 거절 원인이 바뀌기 전에는 같은 요청을 반복하지 않는다.

## 복습 문답, AI 작성

질문: failed와 rejected를 구분하는 이유는?

답안: 실패는 일시 오류일 수 있지만 거절은 정책이나 권한 조건이 맞지 않는 경우다. 같은 조건의 반복은 해결 없이 비용과 차단 위험만 키운다.
