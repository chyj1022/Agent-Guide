## 왜 필요하고 무엇인가

에이전트와 도구 서버가 늘면 인증, 한도와 로깅을 각각 구현할 때 빠뜨릴 가능성이 커진다. 게이트웨이는 공통 제어를 모아 전체 호출을 관찰하고 정책을 일관되게 적용하는 지점이다.

## 입력에서 출력까지

에이전트 요청을 받아 신원과 위임 토큰을 검증하고 허용 도구 목록, 권한, 한도와 정지 상태를 적용한다. 내부 MCP, SaaS 또는 외부 A2A로 전달하고 결과 검사와 감사 기록을 수행한다.

## 원자료의 구체적인 설명

자료는 에이전트 5개와 도구 서버 10개 상황을 예로 든다. 신원, 토큰 교환, 범위 검사, 비용과 횟수, 감사 로그, 카탈로그, 정지 스위치를 한 곳에 두고 에이전트는 게이트웨이만 알게 한다.

## 적합한 조건과 피할 조건

여러 에이전트가 여러 자원에 접근하는 조직에 적합하다. 단순한 단일 도구에 과도한 계층을 붙이거나 게이트웨이에 도메인 판단 전체를 몰아넣는 것은 피한다.

## 한계와 확인할 점

게이트웨이는 단일 장애점과 병목이 될 수 있다. 우회 경로와 직접 자격증명이 남아 있으면 중앙 통제 가정이 깨지고 도구 자체의 최종 권한 검사도 여전히 필요하다.

## 설계 적용, AI 보완

직접 네트워크 경로와 자격증명 발급을 제한하고 게이트웨이는 단순한 정책 집행 역할에 집중시킨다. 이중화, 정책 동기화, 장애 시 거부 동작과 감사 누락을 시험한다.

## 복습 문답, AI 작성

질문: 게이트웨이에 정지 스위치가 있어도 우회를 막아야 하는 이유는?

답안: 에이전트가 다른 경로로 도구를 호출할 수 있으면 중앙 차단이 실제 효과를 막지 못하기 때문이다.
