# AGC-007 작업에 묶는 최소 권한

출처: `SRC-01`, 보관 HTML 앵커 `s-3dc7a874`. [원자료에 기재된 사이트 원문](https://tech-learning-hub.pages.dev/courses/agentic-ai/complete-guide.html#s-3dc7a874). 강의 개념의 재서술이며 개인 구현 성과를 뜻하지 않는다. PDF 쪽 대응과 현행 명세 검증 범위는 출처 색인에서 별도로 확인한다. 원문 링크의 현재 응답은 확인하지 못했고 본문은 보관 HTML을 기준으로 판독했다.

## 왜 필요하고 무엇인가

사람 계정을 그대로 쓰면 그 사람의 모든 권한이 사고 범위가 된다. 작업 토큰은 무엇을, 어느 자원에, 언제까지 할 수 있는지를 함께 좁힌다.

## 입력에서 출력까지

사용자 권한과 작업 요구의 교집합을 계산하고 필수 권한이 빠지면 거부한다. 자원, 작업 ID, 만료와 토큰 식별자를 발급하고 도구가 매 호출 범위, 자원, 만료와 한도를 확인한다.

## 원자료의 구체적인 설명

자료는 사용자 권한 40개 대신 작업 범위 3개와 30분 수명을 대비한다. 환불 10만원 제한을 프롬프트에만 적지 않고 도구가 20만원 요청을 거부하도록 검사하는 것이 핵심이다.

## 적합한 조건과 피할 조건

외부 데이터에 노출되는 에이전트와 계정 또는 금전 변경 도구에 적합하다. 프롬프트나 클라이언트 내부 검사만으로 강제 통제를 구현하려는 접근은 부적절하다.

## 한계와 확인할 점

예시 딕셔너리는 서명과 검증을 갖춘 토큰 서버 구현이 아니다. 원자료의 sub와 act 설명도 RFC 8693의 현재 행위자 의미와 반대이므로 그대로 복사하면 안 된다.

## 설계 적용, AI 보완

발급자, 대상 서비스, 서명과 폐기를 도구 경계에서 검사한다. 실제 actor와 대리 subject를 별도로 관리하고 표준 의미에 맞춰 토큰에 매핑한다.

## 복습 문답, AI 작성

질문: 범위만 제한하면 충분한가?

답안: 모든 자원에 오래 접근할 수 있다면 피해가 여전히 크다. 대상과 시간도 좁히고 매 호출에서 강제해야 한다.

공식 의미 보완: RFC 8693에서 `act`는 현재 행위자를 나타낸다. 대리 대상 subject와 actor를 뒤집지 않는다. [RFC 8693, 4.1](https://www.rfc-editor.org/rfc/rfc8693.html#section-4.1)을 대조했다.
