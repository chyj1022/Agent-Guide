# AGC-018 계획으로 변경 방향을 먼저 검토하기

출처: `SRC-01`, 보관 HTML 앵커 `s-0cfb624a`. [원자료에 기재된 사이트 원문](https://tech-learning-hub.pages.dev/courses/agentic-ai/complete-guide.html#s-0cfb624a). 강의 개념의 재서술이며 개인 구현 성과를 뜻하지 않는다. PDF 쪽 대응과 현행 명세 검증 범위는 출처 색인에서 별도로 확인한다. 원문 링크의 현재 응답은 확인하지 못했고 본문은 보관 HTML을 기준으로 판독했다.

## 왜 필요하고 무엇인가

계획은 구현이 쌓이기 전에 요구 해석과 접근의 차이를 발견하는 저렴한 검토 지점이다. 변경 파일 수, 위험과 검증 방법을 드러내면 결과가 나온 뒤 전체를 버리는 일을 줄인다.

## 입력에서 출력까지

요구사항과 읽기 도구를 주고 이해한 내용, 파일 변경, 접근 이유, 위험, 검증, 열린 질문과 단계 수를 구조화한다. 필요한 결정을 해소한 계획을 실행 입력으로 고정하고 구현 결과를 계획과 비교한다.

## 원자료의 구체적인 설명

자료의 Plan에는 understanding, files_to_change, approach, risks, verification, open_questions가 있다. 예상 3개와 계획 20개 파일의 차이는 요구 해석이 다른 신호이고 단순 테스트 실행이라는 검증 설명은 부족할 수 있다.

## 적합한 조건과 피할 조건

범위와 파급이 큰 변경이나 모호한 요구에 적합하다. 모든 사소한 수정에 기계적으로 승인을 추가하거나 질문을 반드시 만들어 내도록 요구하면 불필요한 지연이 생긴다.

## 한계와 확인할 점

원자료의 계획 도구 목록에 run_tests가 있으나 테스트는 파일이나 DB를 변경할 수 있다. 읽기 전용 계획이라는 목적에 맞게 도구의 실제 효과도 제한해야 한다. 질문이 없다는 사실만으로 추측을 확정할 수 없다.

## 설계 적용, AI 보완

계획에 가정과 승인된 결정을 기록한다. 실행 중 범위가 달라지면 변경 이유와 추가 검증을 갱신하고 실제로 중요한 미정 사항만 사용자에게 확인한다.

## 복습 문답, AI 작성

질문: 계획에서 테스트 실행만 적으면 충분한가?

답안: 어떤 요구 동작과 실패 조건을 어떤 검사로 판정할지 드러나야 한다. 명령 실행 사실만으로 요구 충족을 알 수는 없다.
