# AGC-035 반복되는 도입 실수와 수정 지점

출처: `SRC-01`, 보관 HTML 앵커 `s-51b2b65d`. [원자료에 기재된 사이트 원문](https://tech-learning-hub.pages.dev/courses/agentic-ai/complete-guide.html#s-51b2b65d). 강의 개념의 재서술이며 개인 구현 성과를 뜻하지 않는다. PDF 쪽 대응과 현행 명세 검증 범위는 출처 색인에서 별도로 확인한다. 원문 링크의 현재 응답은 확인하지 못했고 본문은 보관 HTML을 기준으로 판독했다.

## 왜 필요하고 무엇인가

자주 생기는 실패는 모델 성능보다 통제의 위치와 평가 절차에 연결된다. 증상과 수정 지점을 짝지으면 같은 실패를 다른 프롬프트로 반복하는 일을 줄일 수 있다.

## 입력에서 출력까지

시스템 단위 레벨, 프롬프트 한도, 사람 계정, 승인 과다, 검증 부재, 재개 누락, 정지 미시험, 평가 없는 수정, 외부 응답 주입과 도입 목표를 점검한다. 발견마다 담당자와 검증 가능한 수정 항목을 만든다.

## 원자료의 구체적인 설명

자료는 평가셋을 20건으로 시작해 CI에 넣는 방안, 긴 작업의 체크포인트, 외부 응답의 스키마 검증과 데이터 격리, 신원과 위임 체인을 제시한다. 프롬프트의 한도를 도구 코드로 옮기는 것이 반복되는 중심 원칙이다.

## 적합한 조건과 피할 조건

기존 시범 사업의 빠른 진단과 설계 리뷰에 적합하다. 목록을 체크했다는 사실만으로 통제가 실제 작동한다고 보거나 모든 실패를 이 표에 억지로 맞추는 것은 피한다.

## 한계와 확인할 점

20건은 출발점 예시이며 드문 오류나 다양한 집단을 검증하기 충분하지 않다. 도구 코드의 검사도 우회 경로와 권한 누락이 있으면 무력화될 수 있다.

## 설계 적용, AI 보완

각 항목을 관찰 증거, 원인 가설, 수정, 재현 시험으로 연결한다. 규칙을 추가한 뒤 정상 업무가 막히는 부작용과 실제 위험 요청의 거부를 함께 확인한다.

## 복습 문답, AI 작성

질문: 프롬프트만 계속 고치면 어떤 문제가 생기는가?

답안: 평가 기준 없이 변경하면 다른 사례가 깨졌는지 모른다. 고정 평가와 실제 도구 경계의 검사로 행동 변화를 측정해야 한다.
