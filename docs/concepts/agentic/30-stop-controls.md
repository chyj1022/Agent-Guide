# AGC-030 정지 버튼의 실제 효과 검증

출처: `SRC-01`, 보관 HTML 앵커 `s-4bacceb7`. [원자료에 기재된 사이트 원문](https://tech-learning-hub.pages.dev/courses/agentic-ai/complete-guide.html#s-4bacceb7). 강의 개념의 재서술이며 개인 구현 성과를 뜻하지 않는다. PDF 쪽 대응과 현행 명세 검증 범위는 출처 색인에서 별도로 확인한다. 원문 링크의 현재 응답은 확인하지 못했고 본문은 보관 HTML을 기준으로 판독했다.

## 왜 필요하고 무엇인가

정지 버튼이 보이는 것과 실제 효과가 멈추는 것은 다르다. 새 작업 접수, 진행 실행, 발급 토큰, 큐와 외부 위임을 함께 통제해야 한다.

## 입력에서 출력까지

소프트 정지는 새 접수만 막고 기존 실행을 마친다. 하드 정지는 실행을 취소하고 가능한 보상을 수행한다. 최종 차단은 게이트웨이에서 호출을 거부한다. 영향 실행 수와 이유, 담당자와 남은 부분 상태를 반환한다.

## 원자료의 구체적인 설명

자료는 프로세스를 죽여도 토큰이 살아 있거나 큐가 재시작 후 실행되거나 외부 에이전트가 계속 동작하는 사례를 든다. 분기 1회 리허설, 실제 중단 시간 측정, 옛 토큰 호출과 A2A 취소 전달 확인을 제안한다.

## 적합한 조건과 피할 조건

외부 효과와 장시간 실행이 있는 서비스에 적합하다. UI만 비활성화하거나 프로세스 종료만으로 모든 후속 처리가 멈췄다고 보는 설계는 부적절하다.

## 한계와 확인할 점

이미 외부에서 완료된 행동은 정지로 취소되지 않는다. 외부 cancel은 수락과 실제 중단이 다를 수 있으며 원상복구가 불가능한 효과는 별도 후처리가 필요하다.

## 설계 적용, AI 보완

정지 범위를 실행, 에이전트, 팀과 조직으로 구분한다. 호출 중 경합, 큐 재전달, 재시작과 외부 취소 실패를 시험하고 재개 권한과 조건을 명시한다.

## 복습 문답, AI 작성

질문: 정지 후 재시작 시험이 왜 필요한가?

답안: 메모리의 취소 상태만 지웠다면 큐 작업이 되살아날 수 있다. 영속 취소와 재전달 방지를 실제로 확인해야 한다.
