## 정의와 필요한 이유

멀티 에이전트는 다른 도구와 판단 기준이 필요한 역할을 분리하는 구조다. 역할 이름을 늘리는 것만으로 품질이 좋아지지는 않는다.

## 입력에서 출력까지

| 단계 | 구체적 내용 |
|---|---|
| 입력 | 조사와 분석 및 작성이 필요한 목표 |
| 처리 | 감독자가 담당자에게 제한된 일을 주고 결과를 취합한다. 조사에는 읽기, 분석에는 계산, 작성에는 확인된 사실만 제공한다. |
| 출력 | 역할별 근거와 종합 결과 |

## 자료의 예제와 학습 포인트

자료는 감독자형, 순차형과 토론형을 비교한다. 순차 수집과 검증 및 작성은 고정 워크플로일 수 있으며 먼저 단일 에이전트의 실제 한계를 확인하도록 권한다.

자료의 코드와 모델명은 당시 흐름을 이해하기 위한 예시다. 이 문서는 외부 API나 원문 코드를 실행한 결과가 아니다. 구현 전 사용 중인 SDK, 전송 방식과 패키지 버전을 현재 공식 문서와 대조한다.

## 적용할 조건과 피할 상황

도구 권한과 전문 기준을 분리해야 하는 경우에 적합하다. 프롬프트 말투만 다른 역할이라면 복잡성의 이득이 적다.

## 실패 조건과 해석 경계

담당자 사이 텍스트 전달에서 출처가 사라지고 오류가 사실로 굳을 수 있다. 최대 라운드 종료 직전 결과가 작성자의 완성 보고서라는 보장도 없다.

## AI 설계 보완

아래는 원문의 수행 결과가 아닌 **AI 설계 제안과 원문 예시의 한계 분석**이다.

담당 결과를 claim, evidence, uncertainty, status로 구조화한다. 역할 수와 전체 비용을 제한하고 최종 취합의 필수 조건을 검사한다.

## AI 작성 복습 문답
