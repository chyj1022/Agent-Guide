## 정의와 필요한 이유

에이전트 도입 검토는 기능 이름보다 문제의 분기와 반복을 먼저 확인하는 절차다. 불필요한 자율성은 지연과 디버깅 부담을 늘린다.

## 입력에서 출력까지

| 단계 | 구체적 내용 |
|---|---|
| 입력 | 자동화하고 싶은 업무와 대표 요청 |
| 처리 | 한 번 호출로 되는지, 순서가 고정인지, 유한한 분기를 if문으로 표현할 수 있는지 차례로 확인한다. |
| 출력 | 단순 호출, 워크플로, 라우팅 또는 에이전트라는 선택과 이유 |

## 자료의 예제와 학습 포인트

자료는 매일 보고서 메일을 워크플로와 스케줄러로, 문의에 따라 조회하거나 담당자에게 넘기는 일을 에이전트 후보로 설명한다. 호출 5~20회나 비용 배수는 예시적 경고다.

## 적용할 조건과 피할 상황

초기 제품 구조 선정과 에이전트 범위 축소에 적합하다. 기술 유행 자체를 도입 근거로 삼지 않는다.

## 실패 조건과 해석 경계

분기 수만으로 필요성이 결정되지는 않는다. 정해진 분기가 많아도 안정적인 규칙 엔진이 더 적합할 수 있다.
