## 정의와 필요한 이유

요청 라우팅은 쉬운 일을 템플릿이나 한 번 호출로 처리하고 탐색이 필요한 것만 에이전트로 보내는 구조다. 오분류에서 회복할 길이 있어야 한다.

## 입력에서 출력까지

| 단계 | 구체적 내용 |
|---|---|
| 입력 | 인사, 요약 또는 복잡한 조사 요청 |
| 처리 | 정형, 단일, 에이전트로 분류한다. 템플릿이 없거나 단일 결과가 부족하면 상위 처리로 승급한다. |
| 출력 | 답변과 선택된 처리 경로 및 비용 등급 |

## 자료의 예제와 학습 포인트

자료의 1,000건 중 620건 템플릿, 250건 단일, 130건 에이전트 분포는 설명용 예시다. 실제 요청 200건을 먼저 분류해 갈래를 설계하라고 제안한다.

자료의 코드와 모델명은 당시 흐름을 이해하기 위한 예시다. 이 문서는 외부 API나 원문 코드를 실행한 결과가 아니다. 구현 전 사용 중인 SDK, 전송 방식과 패키지 버전을 현재 공식 문서와 대조한다.

## 적용할 조건과 피할 상황

요청 난이도 편차가 큰 서비스에 적합하다. 모든 요청이 복잡하거나 라우터 자체가 비싸면 이득을 측정해야 한다.

## 실패 조건과 해석 경계

모델이 uncertain을 표시하지 않는 오분류는 조용히 잘못 답할 수 있다. 승급 경로가 순환하면 오히려 호출이 늘어난다.

## AI 설계 보완

아래는 원문의 수행 결과가 아닌 **AI 설계 제안과 원문 예시의 한계 분석**이다.

경로별 필수 근거와 결과 검증을 정의한다. 승급 횟수를 제한하고 어려운 사례와 분류 비용까지 포함한 전체 성공률을 잰다.

## AI 작성 복습 문답

**질문:** 정형 경로에 템플릿이 없으면 어떻게 해야 하나?

**설명 답안:** 빈 답을 내기보다 한 번 호출이나 더 적합한 상위 경로로 제한적으로 넘긴다.
