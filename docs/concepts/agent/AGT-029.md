# AGT-029 상태를 DB 에 저장한다

출처: **SRC-02**, 보조 HTML 구간 [#s-b2541d2b](https://tech-learning-hub.pages.dev/courses/ai-agent/complete-guide.html#s-b2541d2b). 사용자 제공 PDF와의 쪽별 대응 및 판독 상태는 [출처 대응표](../../../sources/SRC-02.md)에서 구분한다. 온라인 주소는 보관 HTML의 사이트 원문 링크이며 현재 온라인 내용과의 일치는 확인하지 않았다. 이 문서는 강의 자료를 바탕으로 AI가 재서술한 개념 설명이며 개인의 구현이나 운영 성과 기록이 아니다.

## 정의와 필요한 이유

지속 상태 저장은 서버 재시작과 여러 인스턴스에서도 대화 상태를 복원하는 기반이다. 저장소 선택과 동시성 및 보관 정책을 함께 정한다.

## 입력에서 출력까지

| 단계 | 구체적 내용 |
|---|---|
| 입력 | thread_id별 상태 갱신 요청 |
| 처리 | SQLite나 PostgreSQL에 체크포인트를 기록한다. 같은 대화에 겹친 요청은 잠금이나 버전 검사로 조정하고 오래된 기록을 정리한다. |
| 출력 | 충돌 없이 저장된 상태와 재시작 후 복원 결과 |

## 자료의 예제와 학습 포인트

자료는 MemorySaver, SqliteSaver와 PostgresSaver를 비교한다. Redis SET NX와 TTL을 이용한 대화 잠금, 완료 대화 7~30일 보관이라는 예시 정책도 제시한다.

자료의 코드와 모델명은 당시 흐름을 이해하기 위한 예시다. 이 문서는 외부 API나 원문 코드를 실행한 결과가 아니다. 구현 전 사용 중인 SDK, 전송 방식과 패키지 버전을 현재 공식 문서와 대조한다.

## 적용할 조건과 피할 상황

재시작과 수평 확장이 있는 서비스에 적합하다. 프로세스 내 메모리 저장을 내구성 있는 운영 저장소로 취급하면 안 된다.

## 실패 조건과 해석 경계

예시 잠금은 고정 값 1을 쓰고 무조건 삭제하므로 TTL 만료 뒤 새 소유자의 잠금을 지울 수 있다. 저장소 context 종료 후 핸들을 계속 쓰는 코드도 피해야 한다.

## AI 설계 보완

아래는 원문의 수행 결과가 아닌 **AI 설계 제안과 원문 예시의 한계 분석**이다.

고유 잠금 토큰, 소유권 확인 후 원자적 해제, 갱신 및 fencing 또는 낙관적 버전 검사를 설계한다. 결과 artifact와 체크포인트 보관을 분리한다.

## AI 작성 복습 문답

**질문:** DB 체크포인터만 붙이면 같은 대화의 동시 요청이 안전한가?

**설명 답안:** 아니다. 겹친 상태 갱신과 재실행을 조정할 동시성 정책이 필요하다.
