## Agentic AI, 위임과 조직 통제

- [AGC-001 자동화와 자율성의 경계](../docs/concepts/agentic/01-workflow-autonomy.md): 자동화와 에이전틱 시스템을 가르는 기준은 실행 경로를 누가 결정하는가이다. 워크플로는 사람이 정한 분기를 따르고, 에이전트는 목표와 관찰을 받아 실행 중 다음 행동을 고른다. 따라서 사전에 경로를 검토하는 것만으로 품질과 안전을 판단하기 어렵다.
- [AGC-002 작업마다 정하는 여섯 자율성 수준](../docs/concepts/agentic/02-autonomy-levels.md): 자율성은 시스템 하나의 등급보다 작업별 사람 개입 정책으로 다루는 편이 유용하다. 자료의 L0부터 L5는 제안만 하는 상태부터 지표 중심의 완전 위임까지 설명하는 교육용 분류다.
- [AGC-003 긴 작업과 외부화된 절차가 바꾸는 설계](../docs/concepts/agentic/03-long-work-standards.md): 자료는 변화 방향을 작업 시간 증가, 절차 파일화, 연결 프로토콜 확산으로 묶는다. 새 기능이 늘수록 상태, 버전과 신뢰 같은 운영 책임이 함께 늘어난다는 점이 중심이다.
- [AGC-004 실패를 네 가지 운영 문제로 나누기](../docs/concepts/agentic/04-failure-patterns.md): 그럴듯한 답만 평가하면 승인 피로, 조용한 실패, 맥락 소실, 권한 과다를 놓친다. 이 분류는 모델을 바꾸기 전에 실패한 제어 지점을 찾는 진단 틀이다.
- [AGC-005 되돌림과 피해로 위임 범위 정하기](../docs/concepts/agentic/05-reversibility-impact.md): 위임 수준은 기술 난도보다 되돌릴 수 있는 정도와 오류의 피해로 정한다. 원복 명령이 있다는 사실보다 후속 시스템까지 이전 상태로 돌아가는지 확인하는 것이 중요하다.
- [AGC-006 판단과 실행을 나누는 위임 단위](../docs/concepts/agentic/06-delegation-units.md): 큰 요청에는 조회, 정책 판단, 변경과 발송이 섞인다. 분해하면 낮은 위험의 준비는 자율적으로 하고 실제 부수 효과 앞에서만 근거를 갖춰 승인받을 수 있다.
- [AGC-007 작업에 묶는 최소 권한](../docs/concepts/agentic/07-task-scoped-permissions.md): 사람 계정을 그대로 쓰면 그 사람의 모든 권한이 사고 범위가 된다. 작업 토큰은 무엇을, 어느 자원에, 언제까지 할 수 있는지를 함께 좁힌다.
- [AGC-008 사람 개입을 세 시점으로 설계하기](../docs/concepts/agentic/08-human-oversight.md): 사람 개입에는 행동 전 승인, 진행 감시, 완료 후 검토가 있다. 각각 지연과 관찰 부담이 달라 한 흐름 안의 다른 지점에 배치한다.
- [AGC-009 증거로 자율성을 올리고 빠르게 낮추기](../docs/concepts/agentic/09-autonomy-promotion.md): 승급은 느낌보다 평가와 운영 기록으로 결정해야 한다. 올리는 절차는 신중하게, 사고 시 낮추는 절차는 신속하게 설계한다.
- [AGC-010 분 단위 루프와 시간 단위 작업](../docs/concepts/agentic/10-short-long-runs.md): 시간이 길어지면 메모리 상태와 사용자의 대기를 가정하기 어렵다. 긴 작업은 재개, 비용 누적, 중간 보고와 배포 중 처리까지 처음부터 설계해야 한다.
- [AGC-011 체크포인트와 멱등으로 재개하기](../docs/concepts/agentic/11-durable-execution.md): 재개 실행은 완료 결과를 저장하고 다시 호출돼도 효과가 중복되지 않게 만드는 방식이다. 결과 재사용과 외부 효과 멱등성은 별도 문제다.
- [AGC-012 긴 맥락을 층별로 관리하기](../docs/concepts/agentic/12-context-layers.md): 큰 맥락 창도 모든 시행착오를 계속 담지는 못한다. 필수 목표와 규칙, 선택적 자료, 최근 대화, 임시 흔적을 나눠 예산을 배분한다.
- [AGC-013 필요할 때 읽는 절차 파일](../docs/concepts/agentic/13-skills.md): 스킬은 반복 절차를 파일로 관리하고 관련 작업에서만 읽는 방식이다. 항상 적용되는 지시와 드물게 필요한 긴 정책을 분리해 입력 예산과 변경 추적을 개선한다.
- [AGC-014 서브에이전트로 맥락을 격리하기](../docs/concepts/agentic/14-subagent-isolation.md): 서브에이전트는 단순히 일을 병렬로 나누는 도구가 아니라 탐색의 부산물을 별도 맥락에 두는 장치다. 본체는 목표와 검증 가능한 보고서를 중심으로 판단을 이어 간다.
- [AGC-015 사람의 진행 기록과 기계 트레이스](../docs/concepts/agentic/15-progress-and-traces.md): 진행 기록은 사람이 경로를 이해하고 기다리거나 중단할 판단을 돕는다. 트레이스는 호출과 비용을 재현하고 디버깅하는 구조화 기록이므로 서로 목적이 다르다.
- [AGC-016 코딩 에이전트를 지탱하는 검증 루프](../docs/concepts/agentic/16-coding-feedback-loop.md): 코딩 작업은 빌드, 테스트와 린트로 결과 일부를 즉시 평가할 수 있다. 이 피드백이 구현, 실패 발견과 수정을 반복하게 하며 자율성을 높일 근거가 된다.
- [AGC-017 저장소 규약을 AGENTS.md에 두기](../docs/concepts/agentic/17-repository-instructions.md): 저장소 규약 파일은 매번 반복 설명하던 실행 명령, 금지 사항과 완료 기준을 작업 맥락에 제공한다. 사람이 읽는 소개 문서와 달리 실행 가능한 운영 정보를 중심으로 작성한다.
- [AGC-018 계획으로 변경 방향을 먼저 검토하기](../docs/concepts/agentic/18-plan-before-execution.md): 계획은 구현이 쌓이기 전에 요구 해석과 접근의 차이를 발견하는 저렴한 검토 지점이다. 변경 파일 수, 위험과 검증 방법을 드러내면 결과가 나온 뒤 전체를 버리는 일을 줄인다.
- [AGC-019 에이전트 변경을 리뷰하는 기준](../docs/concepts/agentic/19-agent-change-review.md): 자동 검증을 통과시키려다 검사를 약화하거나 변경 범위를 키우는 일이 생길 수 있다. 리뷰는 결과 코드와 함께 검증 자체의 변화, 기존 구현 재사용과 예외 처리의 의미를 확인해야 한다.
- [AGC-020 작은 이슈로 코딩 흐름 실습하기](../docs/concepts/agentic/20-coding-exercise.md): 실습은 에이전트를 실행해 보는 것보다 검증, 규약, 격리, 계획과 리뷰가 하나의 흐름으로 작동하는지 확인하는 데 목적이 있다. 자료의 과제이며 수행 완료를 뜻하지 않는다.
- [AGC-021 딥리서치의 확장과 수렴](../docs/concepts/agentic/21-deep-research.md): 딥리서치는 질문 하나의 검색 결과로 바로 답하기보다 하위 질문을 만들고 근거의 빈틈과 모순에 따라 조사 범위를 조정한다. 계속 확장될 수 있으므로 수렴 조건이 중요하다.
- [AGC-022 주장과 출처를 분리해 보존하기](../docs/concepts/agentic/22-claims-provenance.md): 인용이 붙었다는 사실만으로 근거가 검증되지는 않는다. 주장과 출처를 분리해 저장하면 어떤 문장이 어떤 원문으로 지지되는지 확인하고 모순과 공백을 드러낼 수 있다.
- [AGC-023 브라우저 조작의 신뢰 경계](../docs/concepts/agentic/23-browser-agents.md): 화면 조작은 도구 API의 좁은 권한 경계를 벗어나 로그인 세션의 넓은 행동을 사용할 수 있다. 따라서 계정, 도메인, 행동, 시간과 기록을 함께 제한해야 한다.
- [AGC-024 도구 연결과 에이전트 위임의 두 층](../docs/concepts/agentic/24-mcp-a2a-layers.md): MCP는 도구와 자원을 연결하는 층이고 A2A는 다른 에이전트에게 일을 위임하는 층이다. 두 연결은 대체 관계보다 한 시스템에서 함께 쓰는 관계로 이해하는 편이 적절하다.
- [AGC-025 Agent Card와 작업 수명주기](../docs/concepts/agentic/25-agent-card-lifecycle.md): 외부 에이전트 내부를 알지 못해도 능력, 접속과 인증 정보를 읽고 위임 여부를 결정할 수 있어야 한다. Agent Card와 작업 상태는 발견과 실행 추적의 서로 다른 계약이다.
- [AGC-026 다른 조직의 에이전트 응답 검증](../docs/concepts/agentic/26-external-agent-trust.md): 프로토콜은 상대가 정직한지, 데이터를 어떻게 쓰는지와 책임을 보장하지 않는다. 외부 에이전트의 결과는 외부 입력으로 취급해 신원과 내용, 비용과 책임을 따로 검토한다.
- [AGC-027 통제를 모으는 게이트웨이](../docs/concepts/agentic/27-control-gateway.md): 에이전트와 도구 서버가 늘면 인증, 한도와 로깅을 각각 구현할 때 빠뜨릴 가능성이 커진다. 게이트웨이는 공통 제어를 모아 전체 호출을 관찰하고 정책을 일관되게 적용하는 지점이다.
- [AGC-028 에이전트 신원과 위임 체인](../docs/concepts/agentic/28-agent-identity.md): 사람 계정으로만 로그가 남으면 실제 행위자와 책임 주체를 구분하기 어렵다. 에이전트 신원, 대리 대상과 재위임 경로를 함께 기록해 누가 누구를 통해 행동했는지 재구성한다.
- [AGC-029 결정 근거를 남기는 감사 로그](../docs/concepts/agentic/29-decision-audit.md): 경로를 스스로 고르는 시스템은 결과만 저장하면 왜 그 행동을 했는지 알기 어렵다. 결정 시점의 사실, 정책과 통제 상태를 구조화하면 사고 원인과 책임, 재현 조건을 검토할 수 있다.
- [AGC-030 정지 버튼의 실제 효과 검증](../docs/concepts/agentic/30-stop-controls.md): 정지 버튼이 보이는 것과 실제 효과가 멈추는 것은 다르다. 새 작업 접수, 진행 실행, 발급 토큰, 큐와 외부 위임을 함께 통제해야 한다.
- [AGC-031 규제 요구를 설계 증거로 바꾸기](../docs/concepts/agentic/31-regulatory-design.md): 규제 대응의 학습점은 법 이름을 나열하는 것보다 위험 관리, 추적성, 인간 감독과 운영 모니터링을 설계 산출물로 연결하는 데 있다. 적용 판단은 용도, 역할과 관할 조건을 먼저 확인해야 한다.
- [AGC-032 조직부터 실행까지의 비용 한도](../docs/concepts/agentic/32-hierarchical-budgets.md): 실행당 한도만으로는 수천 개의 동시 실행이나 재귀 위임의 총비용을 막기 어렵다. 조직, 팀, 에이전트, 사용자와 실행의 한도를 함께 두어 비용과 폭주를 통제한다.
- [AGC-033 첫 도입 업무를 고르는 기준](../docs/concepts/agentic/33-pilot-selection.md): 첫 도입은 가장 아픈 문제보다 결과를 검증할 수 있고 반복 표본이 쌓이는 업무에서 시작하는 편이 학습하기 쉽다. 담당자 협조와 복구 가능성도 기술 성능만큼 중요하다.
- [AGC-034 도입 성과를 읽는 지표 묶음](../docs/concepts/agentic/34-adoption-metrics.md): 호출량은 사용 정도를 보여 줄 뿐 정확성이나 실제 업무 개선을 말하지 않는다. 품질, 자율성, 업무 효과와 안전을 함께 봐야 통제 완화가 타당한지 판단할 수 있다.
- [AGC-035 반복되는 도입 실수와 수정 지점](../docs/concepts/agentic/35-adoption-antipatterns.md): 자주 생기는 실패는 모델 성능보다 통제의 위치와 평가 절차에 연결된다. 증상과 수정 지점을 짝지으면 같은 실패를 다른 프롬프트로 반복하는 일을 줄일 수 있다.
- [AGC-036 운영 통제를 검증하는 단계별 과제](../docs/concepts/agentic/36-control-exercises.md): 실습은 정책 문서 존재보다 실제 제한과 회복 동작을 확인하는 데 목적이 있다. 따라 하기에서 기존 구조를 바꾸고 독립 기준서를 만드는 순서로 검증 깊이를 높인다.
- [AGC-037 검증에서 확장으로 이어지는 도입 순서](../docs/concepts/agentic/37-adoption-sequence.md): 도입의 어려움은 실행 가능한 에이전트를 만드는 것보다 조직이 근거를 보고 맡길 수 있게 하는 데 있다. 검증, 권한, 기록과 정지를 먼저 갖춘 뒤 자율성과 적용 범위를 넓힌다.

## AI Agent, 도구와 실행 상태

- [AGT-001 LLM 호출과 에이전트의 차이](../docs/concepts/agent/AGT-001.md): 단순 호출은 한 번 답을 만들고, 워크플로는 사람이 정한 순서를 따르며, 에이전트는 관찰에 따라 다음 행동을 선택한다. 자율성의 위치가 세 구조를 구분한다.
- [AGT-002 에이전트가 정말 필요한가](../docs/concepts/agent/AGT-002.md): 에이전트 도입 검토는 기능 이름보다 문제의 분기와 반복을 먼저 확인하는 절차다. 불필요한 자율성은 지연과 디버깅 부담을 늘린다.
- [AGT-003 워크플로가 먼저다, 에이전트는 마지막 선택지](../docs/concepts/agent/AGT-003.md): 한 번 호출, 체인, 라우팅, 에이전트는 제어를 모델에 맡기는 정도가 다르다. 필요한 곳에만 판단을 위임해야 운영 경계를 이해하기 쉽다.
- [AGT-004 꼭 알아야 할 용어 정리](../docs/concepts/agent/AGT-004.md): 도구, 스키마, 턴, 궤적, 메모리, HITL은 모델과 실행기의 책임을 나누기 위한 용어다. 같은 단어를 다른 의미로 쓰면 설계와 평가가 엇갈린다.
- [AGT-005 에이전트의 구성 요소](../docs/concepts/agent/AGT-005.md): 에이전트는 모델, 도구, 기억과 계획을 실행 제어로 묶은 시스템이다. 가드레일이 함께 있어야 동작 범위를 통제할 수 있다.
- [AGT-006 처음 만드는 사람이 겪는 다섯 가지 오해](../docs/concepts/agent/AGT-006.md): 초기 오해를 풀려면 판단과 실행을 분리해야 한다. 모델 성능이나 프롬프트만으로 권한과 반복 문제를 해결할 수 없다.
- [AGT-007 함수 호출은 실제로 어떻게 동작하나](../docs/concepts/agent/AGT-007.md): 함수 호출은 질문에서 실행 요청을 만든 뒤 도구 결과를 다시 모델에게 전달하는 왕복 프로토콜이다. 실행과 결과의 대응 관계를 보존해야 한다.
- [AGT-008 도구 설계는 description 이 절반이다](../docs/concepts/agent/AGT-008.md): 도구 설명은 모델이 기능을 선택하는 인터페이스다. 대상, 사용 조건, 제외 조건과 반환 모양이 분명해야 잘못된 선택과 반복을 줄인다.
- [AGT-009 구조화 출력으로 결과 모양을 고정한다](../docs/concepts/agent/AGT-009.md): 구조화 출력은 프로그램이 사용할 결과의 키, 타입과 허용값을 제한하는 방법이다. 모양의 안정성과 내용의 정확성은 별개다.
- [AGT-010 도구가 실패할 때, 재시도, 타임아웃, 회로 차단](../docs/concepts/agent/AGT-010.md): 도구 신뢰성은 타임아웃, 제한된 재시도, 회로 차단과 오류 계약으로 만든다. 실패를 관찰 가능한 상태로 바꾸면 대체 경로를 선택할 수 있다.
- [AGT-011 도구를 병렬로 부른다](../docs/concepts/agent/AGT-011.md): 병렬 도구 실행은 서로 독립된 관찰을 동시에 수집해 지연을 줄인다. 의존성과 부작용이 있으면 실행 순서가 의미를 갖는다.
- [AGT-012 위험한 도구를 감싸는 세 겹](../docs/concepts/agent/AGT-012.md): 위험 도구 방어는 기능을 제거하고 범위를 줄인 뒤 실행 직전 검증과 승인을 적용하는 다층 통제다. 권한 자체가 피해의 상한을 정한다.
- [AGT-013 프레임워크 없이 40줄로 만드는 첫 에이전트](../docs/concepts/agent/AGT-013.md): 작은 직접 구현 루프는 프레임워크가 감추는 왕복을 이해하는 학습 기준선이다. 도구 등록, 명세, 모델 호출, 관찰 추가와 종료가 핵심이다.
- [AGT-014 생각하고, 행동하고, 관찰한다](../docs/concepts/agent/AGT-014.md): ReAct는 다음 행동을 선택하고 실행한 결과를 관찰해 다시 판단하는 반복 구조다. 관찰이 다음 경로를 바꾼다는 점이 중요하다.
- [AGT-015 종료 조건을 설계한다](../docs/concepts/agent/AGT-015.md): 종료 설계는 정상 완료, 상한 중단, 제자리걸음과 사용자 취소를 구분하는 계약이다. 멈춘 이유를 알려야 부분 결과를 완성본으로 오해하지 않는다.
- [AGT-016 무엇을 기억하고 무엇을 버릴 것인가](../docs/concepts/agent/AGT-016.md): 기억은 최근 대화, 현재 작업 상태와 세션을 넘는 사실을 다른 수명으로 관리하는 설계다. 모두 대화 배열에 쌓으면 비용과 맥락 손실이 커진다.
- [AGT-017 컨텍스트가 넘칠 때 압축한다](../docs/concepts/agent/AGT-017.md): 컨텍스트 압축은 정보 종류에 따라 보존, 요약, 외부 보관과 제거를 다르게 적용하는 과정이다. 중요한 결정과 실패를 유지해야 탐색이 되풀이되지 않는다.
- [AGT-018 스트리밍으로 진행 상황을 보여 준다](../docs/concepts/agent/AGT-018.md): 스트리밍은 긴 실행의 진행과 답변을 이벤트로 전달하는 사용자 인터페이스 계약이다. 실행 중 무엇을 하는지와 최종 종료를 구분해 알려야 한다.
- [AGT-019 에이전트는 왜 비싼가](../docs/concepts/agent/AGT-019.md): 에이전트 비용은 반복마다 이전 기록을 다시 입력하는 누적 구조에서 커진다. 호출 횟수뿐 아니라 각 관찰의 길이를 줄여야 한다.
- [AGT-020 라우팅으로 쉬운 요청을 싸게 처리한다](../docs/concepts/agent/AGT-020.md): 요청 라우팅은 쉬운 일을 템플릿이나 한 번 호출로 처리하고 탐색이 필요한 것만 에이전트로 보내는 구조다. 오분류에서 회복할 길이 있어야 한다.
- [AGT-021 캐싱으로 반복 비용을 줄인다](../docs/concepts/agent/AGT-021.md): 캐싱은 고정 입력, 반복 조회와 동일 응답을 다른 계층에서 재사용해 비용을 줄인다. 데이터 신선도와 사용자 범위가 캐시 정확성을 결정한다.
- [AGT-022 계획과 반성](../docs/concepts/agent/AGT-022.md): 계획은 목표를 실행 가능한 단계와 의존성으로 나누고 반성은 결과의 누락과 오류를 점검한다. 검증 수단과 반복 상한이 있어야 추가 호출이 가치를 갖는다.
- [AGT-023 언제 여럿으로 나눌 것인가](../docs/concepts/agent/AGT-023.md): 멀티 에이전트는 다른 도구와 판단 기준이 필요한 역할을 분리하는 구조다. 역할 이름을 늘리는 것만으로 품질이 좋아지지는 않는다.
- [AGT-024 왜 그래프로 만드나](../docs/concepts/agent/AGT-024.md): 상태 그래프는 반복문 안의 판단과 도구 및 중단 분기를 노드와 엣지로 드러내는 표현이다. 흐름이 복잡할 때 상태 저장과 재개를 체계화한다.
- [AGT-025 미리 만들어진 ReAct 에이전트가 가장 빠르다](../docs/concepts/agent/AGT-025.md): 미리 만든 ReAct 생성기는 도구 정의와 모델을 연결해 기본 왕복 루프를 빠르게 구성하는 학습 출발점이다. 간결한 호출 뒤의 제어 책임은 남는다.
- [AGT-026 직접 그래프 만들기: State, Node, Edge](../docs/concepts/agent/AGT-026.md): State는 공유 데이터, Node는 상태 변화, Edge는 다음 실행 위치다. reducer는 여러 갱신이 어떻게 합쳐지는지 정한다.
- [AGT-027 체크포인트로 중단하고 이어서 한다](../docs/concepts/agent/AGT-027.md): 체크포인트는 실행 중 상태와 다음 위치를 저장해 대화와 중단 작업을 이어가는 장치다. 대화 식별자와 저장소 수명이 복구 범위를 정한다.
- [AGT-028 중간에 사람 승인을 넣는다](../docs/concepts/agent/AGT-028.md): 사람 승인 노드는 실행할 동작과 인자를 보여 주고 판단을 받을 때까지 상태를 보류한다. 승인과 실제 실행을 결합해 무단 부작용을 막는다.
- [AGT-029 상태를 DB 에 저장한다](../docs/concepts/agent/AGT-029.md): 지속 상태 저장은 서버 재시작과 여러 인스턴스에서도 대화 상태를 복원하는 기반이다. 저장소 선택과 동시성 및 보관 정책을 함께 정한다.
- [AGT-030 스트리밍과 이벤트로 그래프 안을 들여다본다](../docs/concepts/agent/AGT-030.md): 그래프 스트림은 전체 상태, 변경분, 모델 토큰과 사용자 정의 진행을 다른 관측 목적으로 제공한다. 내부 진단과 사용자 화면에 필요한 정보가 다르다.
- [AGT-031 멀티 에이전트와 관측](../docs/concepts/agent/AGT-031.md): 감독자 그래프는 각 담당자를 노드로 두고 결과에 따라 다음 담당자나 종료를 선택한다. 협업 흐름도 전체 예산과 관측 기준이 필요하다.
- [AGT-032 반드시 넣어야 할 안전장치](../docs/concepts/agent/AGT-032.md): 운영 안전장치는 반복, 자원, 권한, 승인과 정보 흐름의 서로 다른 실패를 각각 제한한다. 하나의 가드만으로 모든 폭주를 막을 수 없다.
- [AGT-033 에이전트 특유의 위험, 프롬프트 인젝션](../docs/concepts/agent/AGT-033.md): 프롬프트 인젝션은 읽은 외부 데이터가 권한 있는 지시처럼 취급되는 문제다. 도구 사용 시스템에서는 잘못된 답을 넘어 정보 유출과 상태 변경으로 이어질 수 있다.
- [AGT-034 무슨 일이 있었는지 알아야 고친다](../docs/concepts/agent/AGT-034.md): 궤적 로깅은 어떤 요청이 어떤 도구와 관찰을 거쳐 끝났는지 재구성하는 자료다. 최종 답만으로는 도구 선택과 실행 실패를 분리하기 어렵다.
- [AGT-035 운영에서 비용과 한도를 지킨다](../docs/concepts/agent/AGT-035.md): 비용 통제는 실행, 사용자, 서비스와 제공사 계층을 나눠 한 요청이나 한 버그가 전체 예산을 소모하지 못하게 하는 설계다.
- [AGT-036 배포, 서버로 감싼다](../docs/concepts/agent/AGT-036.md): 긴 에이전트 실행을 서버로 감싸려면 작업 수명과 HTTP 요청 수명을 분리해야 한다. 큐, 결과 저장과 대화 동시성이 추가로 필요하다.
- [AGT-037 잘 안 될 때 증상별로 짚기](../docs/concepts/agent/AGT-037.md): 증상별 진단은 최종 답을 무작정 수정하기보다 선택, 인자, 실행 결과와 반복을 궤적에서 나누어 보는 방법이다.
- [AGT-038 따라 하기 폭주하는 에이전트를 잡아 고치기](../docs/concepts/agent/AGT-038.md): 폭주 수정 실습은 정보가 없는 실패 응답이 반복 탐색을 부르는 과정을 재현하고 도구 계약을 개선하는 교육 예다.
- [AGT-039 스스로 해 보기](../docs/concepts/agent/AGT-039.md): 단계별 자가 실습은 도구 선택, 실패와 제동을 직접 관찰하고 개선을 측정하도록 구성된 학습 과제다. 과제 제시와 수행 완료는 구분한다.
- [AGT-040 MCP 로 도구를 표준 방식으로 붙인다](../docs/concepts/agent/AGT-040.md): MCP는 여러 호스트가 같은 도구 서버를 공통 규약으로 연결하도록 하는 인터페이스다. 연결 재사용성과 서버 권한을 함께 검토해야 한다.
- [AGT-041 RAG 를 도구 하나로 붙인다](../docs/concepts/agent/AGT-041.md): RAG를 검색 도구로 제공하면 모델이 검색 필요성과 재검색을 선택한다. 고정 검색 파이프라인보다 유연하지만 필요한 검색을 생략하는 실패가 생긴다.
- [AGT-042 코드 실행 도구를 안전하게 준다](../docs/concepts/agent/AGT-042.md): 코드 실행 도구는 계산과 데이터 처리를 검증 가능하게 하지만 생성된 코드를 비신뢰 입력으로 격리해야 한다. 프로세스 분리만으로 파일과 네트워크를 막을 수는 없다.
- [AGT-043 파일과 브라우저 도구](../docs/concepts/agent/AGT-043.md): 파일과 웹 도구는 필요한 구간만 읽도록 탐색과 본문 읽기를 나누는 것이 핵심이다. 경로와 URL은 모델이 제안한 외부 입력으로 검사한다.
- [AGT-044 에이전트를 어떻게 재나](../docs/concepts/agent/AGT-044.md): 에이전트 평가는 최종 정답, 도구 선택, 경로 효율과 올바른 거부를 분리해 측정하는 것이다. 한 점수는 서로 다른 실패를 숨길 수 있다.
- [AGT-045 도구를 단위 테스트한다](../docs/concepts/agent/AGT-045.md): 도구 단위 테스트는 모델 판단을 제거하고 함수의 정상 동작과 경계 및 실패 처리를 확인한다. 그 다음 선택 평가와 전체 실행 평가로 범위를 넓힌다.
- [AGT-046 궤적을 테스트한다, 재현 가능하게 만들기](../docs/concepts/agent/AGT-046.md): 궤적 녹화와 재생은 고정된 모델 응답을 사용해 루프와 금지 행동 및 순서를 반복 검사하는 방식이다. 실시간 모델 품질 평가는 별도로 필요하다.
- [AGT-047 회귀를 막는 CI](../docs/concepts/agent/AGT-047.md): CI 회귀 게이트는 품질, 금지 행동과 비용 기준을 기계적으로 검사해 조용한 성능 저하를 드러낸다. 빠른 오프라인 검사와 유료 평가를 분리한다.
- [AGT-048 이 실습을 하는 법](../docs/concepts/agent/AGT-048.md): 클론 코딩 안내는 열 개 실습을 기초 루프에서 도구 안전, 그래프와 배포까지 연결하는 학습 경로다. 설치 지시와 예상 결과는 실행 사실이 아니다.
- [AGT-049 C-01, 프레임워크 없이 만드는 첫 에이전트](../docs/concepts/agent/AGT-049.md): C-01은 프레임워크 없이 두 도구를 연결해 모델 요청과 실제 실행 및 관찰의 왕복을 확인하는 실습이다.
- [AGT-050 C-02, 파일 정리 에이전트](../docs/concepts/agent/AGT-050.md): C-02는 파일 목록을 보고 정리 계획을 만든 뒤 승인된 이동만 실행하는 실습이다. 경로 범위와 변경 전 확인을 함께 배운다.
- [AGT-051 C-03, SQL 분석 에이전트](../docs/concepts/agent/AGT-051.md): C-03은 자연어 질문을 DB 스키마에 맞는 조회 SQL로 바꾸고 실행 결과를 해석하는 실습이다. 쓰기 제한과 결과 크기 통제가 중요하다.
- [AGT-052 C-04, 웹 조사 에이전트](../docs/concepts/agent/AGT-052.md): C-04는 웹 검색 후보에서 본문을 읽고 실제 근거를 인용해 조사 결과를 작성하는 실습이다. 검색과 읽음 및 인용 검증 상태를 구분해야 한다.
- [AGT-053 C-05, RAG 고객지원 에이전트](../docs/concepts/agent/AGT-053.md): C-05는 작은 규정 검색기를 도구로 붙이고 근거가 없는 질문에서 답을 지어내지 않는 상담 실습이다. 정답뿐 아니라 적절한 미확인 응답을 학습한다.
- [AGT-054 C-06, 코드 리뷰 에이전트](../docs/concepts/agent/AGT-054.md): C-06은 변경 목록과 diff 및 주변 코드를 읽고 리뷰 지적을 구조화해 전달하는 실습이다. 파일 위치와 위험 시나리오를 검증 가능하게 만드는 것이 목적이다.
- [AGT-055 C-07, LangGraph 승인 흐름](../docs/concepts/agent/AGT-055.md): C-07은 조회는 허용하고 송금 모의 동작 앞에서는 중단해 사람 판단 뒤 재개하는 그래프 실습이다. 대기 상태와 부작용 상태가 다르다는 점을 배운다.
- [AGT-056 C-08, MCP 서버를 만들고 붙인다](../docs/concepts/agent/AGT-056.md): C-08은 메모 기능을 MCP 서버 한 벌로 노출하고 여러 호스트에서 도구를 사용하는 실습이다. 표준 연결과 서버 자체의 경로 및 쓰기 책임을 배운다.
- [AGT-057 C-09, 멀티 에이전트 리서치 팀](../docs/concepts/agent/AGT-057.md): C-09는 독립 하위 작업을 동적으로 나눠 병렬 결과를 모으고 단일 방식과 비교하는 실습이다. 분산 자체보다 측정 가능한 이득을 확인하는 것이 목적이다.
- [AGT-058 C-10, 평가 세트와 API 배포](../docs/concepts/agent/AGT-058.md): C-10은 상담 루프를 평가 계약과 API로 감싸 서비스 형태를 연습하는 단계다. 평가 실행과 서버 포장이 운영 완성을 자동 보장하지는 않는다.
- [AGT-059 마무리와 다음 단계](../docs/concepts/agent/AGT-059.md): 마무리 학습 경로는 작은 읽기 전용 시스템에서 시작해 관측과 제동을 갖춘 뒤 필요한 쓰기와 평가를 더하는 순서다. 도구 품질과 실행 통제가 모델 선택만큼 중요하다.
