# MCP를 연결할 때 설계할 것

AGT-040, AGT-056, AGC-024~027의 개념을 연결한 AI 보완 지침입니다. MCP는 도구와 데이터 접근을 연결하는 프로토콜입니다. 작업 순서를 고르는 에이전트나 권한을 판단하는 하네스 전체가 아닙니다.

## 역할과 프리미티브

Host는 모델과 사용자 동의, 컨텍스트를 조정합니다. Host 안의 Client는 특정 Server와 통신하고, Server는 한정된 능력을 제공합니다. Tools는 실행 기능, Resources는 읽을 수 있는 자료, Prompts는 재사용할 입력 틀로 구별합니다. 서버가 제공한 설명은 선택을 돕지만 신뢰 경계를 넘는 권한을 부여하지 않습니다.

2026-10-31에 확인한 [MCP 2026-07-28 architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture)는 요청마다 버전과 능력을 담는 stateless 구조를 설명합니다. 강의의 이전 SDK 예제나 초기화/세션 가정을 모든 버전에 적용하지 마세요. 한 클라이언트와 한 서버의 대응, Host의 정책 책임을 구현에서 확인합니다. 이 저장소는 해당 버전의 실서버 연결을 실행하지 않았습니다.

## 버전 고정 카드

```text
host=미정,client_sdk=미정,server_sdk=미정
protocol_version=미정,transport=stdio또는지원HTTP
server_origin=미정,owner=미정,required_tools=미정
auth=미정,scope=미정,allowed_resources=미정
startup_command=미정,health_check=미정,compatibility_test=미정
```

사양 버전, 라이브러리 버전, 서버 제품 버전은 서로 다릅니다. 서버가 “MCP 지원”이라고 써 있어도 선택한 Host가 그 서버의 기능과 전송 방식을 지원하는지 확인해야 합니다. 버전 카드가 없으면 설치 명령만 복사해서 붙이는 방식의 장애를 반복하기 쉽습니다.

## 연결 순서

1. 실제 필요한 도구 이름과 최소 읽기/쓰기 범위를 정합니다. 공개 서버라고 전부 연결하지 않습니다.
2. 서버 운영자, 실행 명령, 의존 패키지, 네트워크 및 파일 접근 범위를 확인합니다. `stdio` 서버는 내 컴퓨터의 프로세스라는 점을 기억합니다.
3. 버전과 전송 방식에 맞는 연결을 만든 뒤 목록과 스키마를 조회합니다.
4. 가짜 입력으로 성공, 잘못된 인자, 권한 거부, 지연, 빈 결과를 시험합니다.
5. 실제 자격 증명과 제한된 데이터로 계약 테스트를 하고 이후에 모델의 도구 선택을 연결합니다.
6. 운영 중 도구 목록이나 스키마가 바뀌면 승인과 평가 기준도 재검토합니다.

## 인증은 전송 방식과 함께 읽기

[2026-07-28 authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)은 HTTP 전송의 인증 흐름을 설명하고, stdio에는 환경에서 자격 증명을 받는 방식을 구분합니다. 인증을 적용하는 HTTP 서버는 해당 OAuth 기반 요구를 따라야 합니다. 환경 변수의 비밀값을 모델 맥락이나 로그에 그대로 넣지 마세요. 이 문서의 간단한 카드가 인증 구현 명세를 대체하지 않습니다.

## MCP와 A2A 구별

데이터 조회와 기능 호출 연결이 목적이면 MCP를 검토합니다. 독립된 원격 에이전트에게 작업을 맡기고 상태와 산출물을 주고받아야 한다면 A2A를 검토할 수 있습니다. [A2A 공식 사양](https://a2a-protocol.org/latest/specification/)에는 Agent Card, 작업 메시지, 취소와 비동기 전달 등이 정의됩니다. `latest` 링크는 움직이므로 실제 구현은 선택한 사양 버전을 별도로 고정하세요. Agent Card의 능력 광고와 사용자에 대한 실제 접근 권한은 별개입니다.
