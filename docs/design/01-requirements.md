# 요구사항에서 에이전트 필요성을 결정하기

이 문서는 강의의 워크플로 우선 원칙과 위임 개념을 앱 설계에 적용한 AI 보완 지침입니다. 관련 주제는 AGT-001~006, AGC-001~009입니다.

## 사용자의 말에서 실행 가능한 문제로

“추천 사이트를 만들어 줘”만으로는 좋은 구조를 고를 수 없습니다. 누구에게 무엇을 비교하는지, 데이터는 어디에서 오는지, 추천 이후 실제 구매까지 하는지를 먼저 구분합니다. 출력이 글인지, 계산 결과인지, 외부 시스템의 변경인지에 따라 실패의 대가가 달라집니다.

요구사항은 `사용자/상황/입력/필요 결과/완료 조건/금지 행동`으로 씁니다. 예를 들어 가상 GPU 가격 비교 앱은 “연구자가 GPU 모델, 지역, 사용 시간을 입력하면, 같은 통화와 청구 단위로 비교 가능한 상품만 정렬하고 근거와 수집 시점을 보여 준다”가 됩니다. 구매나 예약이 없다면 결제 도구는 필요 없습니다.

## 가장 작은 실행 구조 선택

| 질문 | 설계 후보 | 확인할 한계 |
| --- | --- | --- |
| 입력과 계산 순서가 고정인가 | 일반 함수와 화면 | LLM 없이도 충분한가 |
| 텍스트 해석만 유동적인가 | LLM 한 번 + 검증 코드 | 해석 스키마와 애매한 조건 처리 |
| 분기가 미리 알려져 있는가 | 명시적 워크플로 | 모든 분기의 종료 조건 |
| 실행 중 관찰에 따라 다음 행동을 골라야 하나 | 제한된 단일 에이전트 | 허용 도구, 횟수, 예산, 실패 처리 |
| 독립 작업을 나누면 실제 이득이 있나 | 병렬 작업 또는 다중 에이전트 | 통합 책임과 비용, 상태 충돌 |

병렬 함수 호출이 곧 멀티 에이전트는 아닙니다. 한 에이전트에게 역할을 여러 개 설명했다고 독립적인 검증이 생기는 것도 아닙니다. 분업 전후의 품질, 지연, 비용을 같은 평가셋으로 비교해야 합니다.

## 완료 조건은 결과와 경계를 함께 적기

가상 가격 비교 앱에서는 정규화된 단위가 다르면 순위를 만들지 않고 “비교 불가”로 표시하게 합니다. 누락 가격을 0으로 채우지 않습니다. 필터 조건과 결과가 일치하고 각 값에 출처와 시점이 있어야 합니다. 이러한 조건은 모델에게 “정확히 답해”라고 말하는 대신 코드와 평가 사례로 검사할 수 있습니다.

권한과 자율성은 기능별로 정합니다. 파일 읽기, 분석, 보고서 초안 작성은 자동화하더라도 외부 게시나 결제는 별도 승인을 요구할 수 있습니다. 다만 실제 권한은 이번 사용자 요청과 제품 정책에 근거해야 합니다. 모든 행동에 무조건 승인을 추가하는 설계도 피로와 지연을 만듭니다.

## 설계 전에 남길 미확정 사항

데이터 사용 권한, 최신성 요구, 허용 네트워크, 개인정보 범위, 예산 상한, 실제 변경 권한, 장애 시 책임자를 모르면 미확정으로 기록합니다. 상상을 사실로 채우지 말고, 진행 가능한 독립 작업과 결정을 기다릴 작업을 나눕니다. 결과는 [APP_SPEC](../../templates/APP_SPEC.md)에 기록합니다.
